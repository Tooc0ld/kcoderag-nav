## Critical Issues

### CR-01: Filesystem identity checks remain check-then-use and can escape the project or delete replacement data

**Classification:** BLOCKER
**Files:**
`D:/AIProgram/kcoderag-nav/src/core/transaction.cts:144-159,208-230,258-298,311-326,368-426,432-479`;
`D:/AIProgram/kcoderag-nav/src/hosts/cursor.cts:726-778,835-927`
**Issue:** The transaction records directory identities and calls `assertParentIdentities`, but every
subsequent read, stage creation, rename, unlink, recovery write, cleanup, and rollback still opens the
object by pathname. An attacker or concurrent process can replace a verified directory after the
assertion and before the path operation. `createRecovery` is weaker still: it creates and populates a
path beneath `desired.target.root` without any identity recheck. The deterministic test swaps only in
`onAfterValidation`, before the first recheck, so it does not exercise this remaining window.

Cursor legacy migration has the same data-loss risk outside the transaction. It verifies the legacy
tree once, performs the whole project transaction, then unlinks each saved pathname without
revalidating its type, digest, or parent identity. A replacement file arriving in that interval is
deleted even though KCodeRag never owned those replacement bytes; rollback also recreates paths with
plain recursive `mkdirSync`/`writeFileSync` and can follow a swapped ancestor.

**Fix:** Bind operations to verified directory handles and no-follow/descriptor-relative primitives.
Where Node cannot provide an equivalent on a supported platform, fail closed instead of claiming the
atomic project boundary. At minimum, add operation-adjacent and post-operation identity checks plus a
deterministic seam between the final check and each read/rename/unlink/recovery operation; for legacy
deletion, re-read and compare each exact file and parent immediately before unlink and never restore
through an unverified ancestor.

### CR-02: Section-owned JSON updates rewrite and can corrupt unrelated configuration

**Classification:** BLOCKER
**Files:**
`D:/AIProgram/kcoderag-nav/src/hosts/claude.cts:105-129,188-220,250-293,538-595`;
`D:/AIProgram/kcoderag-nav/src/hosts/codex.cts:79-89,541-584,984-1034`;
`D:/AIProgram/kcoderag-nav/src/hosts/cursor.cts:85-99,130-138,206-245`
**Issue:** Durable digests are now section-scoped, but every shared JSON mutation still parses the
entire user document into JavaScript objects and serializes the entire object back. That changes
unrelated lexical content and can change unrelated values: for example, a valid unowned integer
literal `9007199254740993` is rounded by `JSON.parse` to `9007199254740992` and is then permanently
written back by install. Escaped string spellings and arbitrary whitespace are also normalized.
Because the credential-safe state no longer stores the original shared file, uninstall cannot
restore those bytes. Existing “exact bytes” fixtures use JSON already matching the serializer and do
not cover lossless unowned values or formatting. This violates the declared section-only ownership
boundary and creates silent user-configuration data loss.

**Fix:** Perform a syntax-aware byte splice that replaces/removes only the owned object member or
array element while leaving every unowned byte untouched. If whole-document parsing is retained for
validation, use it only to locate/validate the owned range, not to render unrelated content. Add
lifecycle tests with noncanonical whitespace, escaped strings, and integers beyond JavaScript's safe
integer range and assert exact byte preservation outside the managed range after install, update,
and uninstall.

## Warnings

### WR-01: A successful release commit can still survive an immediate follow-up Git failure

**Classification:** WARNING
**File:** `D:/AIProgram/kcoderag-nav/src/maintainer/release.cts:348-395`
**Issue:** `git commit` runs at line 367, but `releaseCommit` is assigned only after a separate
`git rev-parse HEAD` succeeds. If the commit succeeds and that follow-up command fails, the catch
branch sees `releaseCommit === undefined` and restores only the seven files/index; it does not reset
HEAD or remove a tag. The current failure injection begins after the assignment, so the passing
post-commit test cannot detect this gap. The release command can therefore report failure while
leaving the repository advanced to the release commit.

**Fix:** On every catch, compare the current HEAD with the captured `originalHead` and establish
whether the exact expected release commit was created before choosing compensation. Record the
commit from a command whose successful result is inseparable from commit creation, or safely
discover and validate the exact child commit/write set before resetting. Add an injected failure
between `git commit` and `rev-parse HEAD`.

### WR-02: Expired session-less marker renewal permits multiple 24-hour claims

**Classification:** WARNING
**File:** `D:/AIProgram/kcoderag-nav/src/hooks/update-check.cts:167-233`
**Issue:** The new marker is stable across hour boundaries, but expiry is renewed with
read-then-`remove`-then-`createExclusive`. Two hook processes can both read the expired timestamp;
one can replace it, then the other can remove that fresh marker and successfully create another.
Both return `true` and spawn detached workers. The worker lock only collapses overlapping workers;
if the first completes before the second claims its lock, both can perform a registry request. Thus
the promised stable 24-hour claim is not upheld under normal concurrent hook invocation.

**Fix:** Renew with a token/compare-and-swap protocol that can delete or replace only the exact stale
marker observed by the claimant, or use a per-project lock held across timestamp validation and
replacement. Add a deterministic interleaving test in which two claimants read the same expired
marker and assert that exactly one schedule succeeds.
