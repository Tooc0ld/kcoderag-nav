## User Constraints (from CONTEXT.md)

### Locked Decisions

### 迁移边界与安装入口

- **D-01:** 完整迁移 Hook、更新检查、项目/Cursor 安装器、生成器、pre-commit 和测试；发布包不再包含 Python 运行代码。— **Reversibility:** costly — 恢复 Python 会同时改动安装契约、生成产物、CI 和全部测试入口。
- **D-02:** 使用 TypeScript 作为维护源码，构建出可直接由 Node.js 执行的 CJS；禁止 `ts-node` 或用户机器上的运行时编译。
- **D-03:** `npx` 完全替代 Codex、Claude Code 与 Cursor 的 marketplace 用户安装流程；当前交付不再依赖任一宿主的 marketplace。— **Reversibility:** costly — 恢复 marketplace 需要重新维护三套宿主分发元数据、安装说明和升级路径。
- **D-04:** 未传 `--host` 时交互选择 Codex、Claude Code 或 Cursor；自动化使用 `--host codex|claude|cursor`，一次命令只修改所选宿主。
- **D-05:** 旧 Python 安装原地安全迁移：读取旧 `install-state.json`，校验受管内容无漂移后原子替换为 JS/CJS，保留当前 QA/Dev；漂移时写前硬停止，只删除能够确认由旧安装器管理的 Python 文件。

### npm 发布与版本语义

- **D-06:** 发布未 scoped 公共包 `kcoderag-nav`，标准入口为 `npx kcoderag-nav@latest install`。— **Reversibility:** one-way — 包名和命令一旦发布并被项目文档引用，就成为外部安装契约，改名需要兼容包和用户迁移。
- **D-07:** 根目录 `package.json` 是唯一版本源；npm 包、QA/Dev/Cursor manifest 和安装状态都从该版本生成。— **Reversibility:** costly — 更换版本源会影响发布、生成器、更新检测和已安装状态比较。
- **D-08:** 使用 `npm run release:patch|minor|major` 生成 `vX.Y.Z` 标签；GitHub Actions 在标签上测试、构建并发布，普通 `master` push 只测试、不发布。
- **D-09:** 异步更新检查查询 npm Registry 的 `kcoderag-nav` `latest`；每会话首次相关工具调用只启动后台刷新，缓存 24 小时并 fail-open，升级提示使用 `npx kcoderag-nav@latest update`。

### 宿主项目边界与落盘位置

- **D-10:** 不使用 marketplace 后，直接管理宿主官方项目配置：Codex 使用 `.codex/` 与 `.agents/skills/`；Claude Code 使用 `.claude/settings.json`、`.claude/skills/` 和项目根 `.mcp.json`；Cursor 使用 `.cursor/rules/`、`.cursor/skills/` 和 `.cursor/mcp.json`。这套能力对外称为 KCodeRag Nav 项目集成，不声称是 marketplace plugin。— **Reversibility:** costly — 路径成为已安装项目中的持久配置和卸载所有权边界。
- **D-11:** `install` 默认目标是当前目录；写入前展示规范化绝对路径并确认。`--target PATH` 可覆盖，不自动寻找 Git/SVN 根。
- **D-12:** 对已有 JSON/配置进行结构化合并，只拥有 KCodeRag section 和独占受管文件；保留无关配置。受管 section 或文件漂移时，`update`/`uninstall` 在写入前硬停止。
- **D-13:** 同一项目允许 Codex、Claude Code、Cursor 跨宿主共存；每次调用只安装一个宿主，可重复执行增加其他宿主。QA/Dev 只在同一宿主内部互斥，跨宿主 QA 共存是正常状态。
- **D-14:** 安装器核心使用可扩展 host adapter 接口，便于未来增加 OpenCode，而不要求重写事务、状态和所有权逻辑。

### Node 兼容与失败恢复

- **D-15:** 最低支持 Node.js 22；CI 同时覆盖 Node.js 22 与 24 LTS，不支持已经 EOL 的 Node.js 20。
- **D-16:** `install`/`update` 在任何项目写入前检查 Node.js 22+，不满足时硬停止；已经部署的 hook 若 Node 缺失、版本损坏或启动异常，必须静默 fail-open；`status`/`doctor` 明确报告运行时问题。
- **D-17:** 首次 `npx` 获取包因 npm/网络失败时给出明确错误且不写目标项目；已安装 hook 完全离线运行；后台更新检查使用缓存并静默 fail-open，网络失败不得进入工具调用的阻塞路径。
- **D-18:** 每次安装或更新是单宿主原子事务：先完成所有校验并生成写入计划，再备份本次涉及的文件；任何一步失败都恢复该宿主安装前状态，不回滚或改动同项目其他宿主。

### the agent's Discretion

- TypeScript 源码的内部目录拆分、类型组织、编译器和测试运行器由规划与实现决定，但必须满足 Node.js 22+、发布 CJS、无运行时编译和发布包无 Python 运行代码。
- 原子写入所用的临时文件命名、备份格式和内部事务 API 可按现有跨平台约束设计；不得削弱写前漂移检查或单宿主回滚边界。
- CLI 的提示文案、颜色和进度呈现可采用常规跨平台 CLI 体验，但自动化的 `--json` 输出必须稳定且不混入诊断噪音。

### Deferred Ideas (OUT OF SCOPE)

- OpenCode 支持作为后续独立能力：新增 host adapter 与真实宿主验证；Phase 03.1 只保证架构可扩展，不交付 OpenCode。
- 生产级个人/组织身份、HTTPS 与凭据轮换继续留在 Phase 8，不在本次运行时迁移中扩大安全范围。

## Summary

The dependency gate can proceed with the two proposed direct development dependencies and no production dependency: `typescript` at `>=5.7.0 <7.0.0` and `@types/node` at `>=22.0.0 <23.0.0`. On 2026-08-23 those ranges resolve at their upper end to `typescript@6.0.3` and `@types/node@22.20.1`; the committed lockfile must pin the exact resolved graph. `typescript@7.0.2` is the registry `latest` but is intentionally excluded by the audited range. [VERIFIED: npm registry package metadata and range queries]

`typescript` is an official Microsoft compiler package and passed the GSD legitimacy seam with `OK`. `@types/node` is the official DefinitelyTyped Node declaration package; the seam returned `SUS: too-new` because it evaluated the package family's current modification date, while the exact audited `22.20.1` was published 2026-07-08 and the package family was created in 2016. Official npm metadata, the DefinitelyTyped publishing documentation, the Microsoft `types` publisher, absence of lifecycle scripts, and registry integrity/signature data are sufficient for the existing blocking-human checkpoint to approve this exact range; the automated `SUS` result must still be recorded rather than rewritten as `OK`. [CITED: https://github.com/DefinitelyTyped/DefinitelyTyped/blob/master/README.md] [CITED: https://registry.npmjs.org/@types%2Fnode/22.20.1]

`@types/node@22.20.1` has one transitive declaration dependency, `undici-types@~6.21.0`, which currently resolves to `6.21.0`. Official Undici documentation says this is the types-only dual publication used by `@types/node`; it has no lifecycle scripts or further dependencies. It belongs only in the development dependency graph, not in `dependencies`. [CITED: https://github.com/nodejs/undici/blob/main/types/README.md] [CITED: https://registry.npmjs.org/undici-types/6.21.0]

**Primary recommendation:** approve the two requested ranges, create and commit `package-lock.json`, run installs with lifecycle scripts disabled, and keep `dependencies` empty unless later runtime code imports a non-Node module.

The `typescript` lower-bound token `5.7.0` is a valid SemVer boundary even though the first stable `5.7.x` versions present in npm are `5.7.2` and `5.7.3`; it does not cause npm to select a nonexistent version. [VERIFIED: npm registry `typescript` version and engine queries]

The `@types/node` package's `22` major line is the Node.js 22 declaration line. Version `22.20.1` exposes `index.d.ts`, has a `typesVersions` fallback only for TypeScript `<=5.6`, and therefore uses its main declarations for the audited TypeScript `>=5.7.0` range. [CITED: https://registry.npmjs.org/@types%2Fnode/22.20.1] [CITED: https://github.com/DefinitelyTyped/DefinitelyTyped/blob/master/README.md]

Use Node-aware emit rather than a runtime transpiler: `.cts` is the explicit CommonJS source marker, TypeScript's Node module modes emit CommonJS or ESM according to file/package markers, and Node.js treats `.cjs` as CommonJS. [CITED: https://www.typescriptlang.org/tsconfig/module.html] [CITED: https://github.com/nodejs/node/blob/v22.17.0/doc/api/packages.md]
