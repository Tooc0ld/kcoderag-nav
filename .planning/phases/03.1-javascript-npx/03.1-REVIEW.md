## Critical Issues

### CR-01: Recovery cleanup recursively deletes replacement data after detecting an identity swap

**Classification:** BLOCKER
**File:** `D:/AIProgram/kcoderag-nav/src/core/transaction.cts:398-425,501-504,549-563`
**Issue:** `writeSecureFile` correctly detects that the recovery directory or destination identity
changed, but `createRecovery` catches that error and immediately runs recursive `rmSync` on the same
pathname without checking which directory is there. `removeRecovery` has the same final
check-then-`rmSync` window. A deterministic `recovery-write` interleaving renamed the verified
recovery directory aside, installed a replacement directory containing a sentinel, and allowed the
identity check to fail. `applyTransaction` returned `transaction_failed`, but the replacement
sentinel was deleted while the original recovery directory survived. This is direct user-data loss
inside the project boundary and means the prior identity finding is not fixed.
**Fix:** Never recursively remove an uncertain pathname. Retain the recovery tree on any identity
mismatch, or quarantine the exact verified object with post-rename identity validation before
cleaning it. Where Node cannot bind recursive deletion to a directory handle, delete only individually
verified private files and non-recursively remove proven-empty directories; add the reproduced
`recovery-write` swap case and a final cleanup-window swap case.

### CR-02: Cursor migration deletes the only backup when the second legacy deletion fails

**Classification:** BLOCKER
**File:** `D:/AIProgram/kcoderag-nav/src/hosts/cursor.cts:870-899,1052-1075`
**Issue:** `removeLegacyQuarantine` irreversibly removes the quarantined plugin tree before it checks
and unlinks the quarantined legacy state. If any error occurs after the plugin removal, rollback calls
`restoreLegacyQuarantine`, which cannot restore the now-absent plugin. Despite that failed restore,
the next rollback block still restores the project and calls `removeMigrationBackup`, deleting the
only remaining copy of the plugin. A deterministic exception at `remove-state-quarantine` produced
`rollback_failed` with `legacyPluginSurvived=false`, `legacyStateSurvived=true`, and
`migrationBackups=0`. The reported recovery path therefore no longer exists and the legacy plugin
data is lost.
**Fix:** Keep the project migration backup until legacy restoration has been fully verified, and
never call `removeMigrationBackup` after `rollbackFailed` becomes true. Restore a missing quarantine
from the verified backup payloads, not only by renaming the quarantine path. Add failures between the
plugin removal, state verification, and state unlink and assert the complete legacy and project trees
are restored or a real retained recovery tree contains every missing byte.

### CR-03: Successful uninstall removes pre-existing shared JSON parent containers

**Classification:** BLOCKER
**Files:**
`D:/AIProgram/kcoderag-nav/src/hosts/claude.cts:595-667`;
`D:/AIProgram/kcoderag-nav/src/hosts/codex.cts:1031-1068`;
`D:/AIProgram/kcoderag-nav/src/hosts/cursor.cts:257-277`
**Issue:** The new splice layer preserves unowned lexical bytes during section replacement, but
uninstall decides to remove `mcpServers`, `hooks.PreToolUse`, and `hooks` solely because they are
empty after removing KCodeRag. `ManagedSectionRecord` remembers only whether the whole file existed,
not whether these parent containers existed before installation. Consequently an original
`{"mcpServers":{}}` or `{"hooks":{"PreToolUse":[]}}` is silently changed on uninstall. Fresh CLI
lifecycle probes for Cursor, Claude, and Codex all exited 0 for install and uninstall while failing
exact-byte comparison against these original fixtures. This violates section-only ownership and is
user-configuration data loss.
**Fix:** Persist ownership/provenance for every parent container created by installation and remove a
container only when the installer created it and it remains empty and unchanged. Existing empty
parents must remain byte-for-byte intact. Add install/update/uninstall tests for pre-existing empty
`mcpServers`, `hooks`, and `PreToolUse` containers in all three adapters.

### CR-04: npm publication can complete while required Node 22 or Windows CI is failing

**Classification:** BLOCKER
**Files:**
`D:/AIProgram/kcoderag-nav/.github/workflows/release.yml:15-49`;
`D:/AIProgram/kcoderag-nav/.github/workflows/ci.yml:15-24`;
`D:/AIProgram/kcoderag-nav/tests/maintainer/release-workflow.test.cts:19-50`
**Issue:** The tag-triggered release job tests only `ubuntu-latest` on Node 24 and then publishes.
The required Windows/Linux by Node 22/24 matrix lives in a separate CI workflow. Both workflows start
independently on a tag, and the publish job has no `needs` or reusable-workflow dependency on that
matrix, so npm publication can finish before the Node 22 or Windows jobs fail. The workflow contract
test verifies only the single Node 24 publish job and even prohibits cross-workflow gating. A package
can therefore be publicly released without passing its declared minimum runtime and supported
platform contract.
**Fix:** Put an explicit Windows/Linux by Node 22/24 verification job in the release workflow (or call
a reusable required workflow) and make the credential-bearing publish job depend on every lane.
Keep `NODE_AUTH_TOKEN` scoped only to the final dependent job. Extend the workflow tests to prove
publish cannot start unless all required lanes succeed.

## Warnings

### WR-01: A transient marker replacement failure permanently disables session-less renewal

**Classification:** WARNING
**File:** `D:/AIProgram/kcoderag-nav/src/hooks/update-check.cts:221-235,275-291`
**Issue:** On any exception from `files.replace`, the renewal token is intentionally retained. Token
pruning treats a token whose contents still equal the marker as active forever, and every later
claimant fails `createExclusive` for the same marker generation. There is no lease or recovery path.
A deterministic filesystem adapter that failed one replacement produced a successful initial claim,
a failed renewal, a failed retry one full TTL later, and one retained token. A transient disk or
rename error can therefore suppress update awareness indefinitely rather than merely fail open for
that invocation.
**Fix:** In the replacement catch path, re-read the marker. If it still equals the observed stale
generation, remove the owned token so a later call can retry; if it equals the proposed new contents,
treat the renewal as completed; retain the token only for a genuinely ambiguous third state. Add a
transient-failure-then-retry test and a bounded stale-token recovery rule.
