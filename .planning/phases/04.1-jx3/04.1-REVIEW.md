## Critical Issues

### CR-01: JX3-only Claude installs deploy a dispatcher whose mandatory dependency is absent

**Classification:** BLOCKER  
**File:** `src/hooks/pre-tool-dispatcher.cts:6` (related projection: `src/hosts/claude.cts:378-387`)  
**Issue:** The dispatcher statically imports `./grep-nudge.cjs` before its fail-open contributor boundary can run. The Claude JX3 contribution installs the JX3 handler, dispatcher, once marker, and launchers, but it does not install `grep-nudge.cjs`; that file is supplied only by the navigation contribution at `src/hosts/claude.cts:328-366`. Therefore the documented and tested `JX3 -> navigation` additive order is broken after the first command, and removing navigation from a dual-capability project breaks the remaining JX3 hook the same way. The launcher hides the module-load failure and exits zero, so users receive no JX3 prompt and diagnostics do not identify the missing runtime. The lifecycle test at `tests/cli/commands.test.cts:809-828` checks files only after both installations and misses the intermediate supported state.

**Fix:** Make navigation loading optional/lazy in the dispatcher, just as update-notice loading is optional, or declare/install `grep-nudge.cjs` as a shared runtime dependency of the JX3 contribution. Add installed-runtime tests that invoke the native launcher immediately after a JX3-only install and after partial navigation uninstall.

```ts
const navigation: NavigationModule | undefined = (() => {
  try { return require("./grep-nudge.cjs") as NavigationModule; }
  catch { return undefined; }
})();
// Call navigation?.navigationContribution(...), while keeping JX3 independent.
```

### CR-02: Drifted and invalid installations return `ok: true` and exit zero

**Classification:** BLOCKER  
**File:** `src/cli/commands.cts:477`  
**Issue:** Read-only commands compute success as `status.status !== "source_conflict"`. Consequently `drifted` and `invalid` states are serialized with `ok: true` and return exit code 0 at line 505. This directly violates the Phase 04.1 diagnostic contract that capability drift is `ok:false`, and makes automation treat corrupted state, managed-file digest mismatches, or orphaned managed roots as healthy. The regression is explicitly cemented by `tests/cli/commands.test.cts:956-963`, which expects a drifted public CLI invocation to exit 0.

**Fix:** Define success from an explicit healthy-state allowlist and return nonzero for `drifted`, `invalid`, and `source_conflict`. Update JSON and human-mode tests to assert `ok:false`, a stable issue code, and exit 1 for unhealthy status/doctor results.

```ts
const ok = status.status === "healthy" ||
  status.status === "not_installed" ||
  status.status === "update_available";
```

### CR-03: The production all-mutation source gate does not inspect native raw/manual configuration

**Classification:** BLOCKER  
**File:** `src/hosts/codex.cts:260-263` (same defect in `src/hosts/claude.cts:429-434`, `src/hosts/cursor.cts:108`, and `src/hosts/opencode.cts:109`)  
**Issue:** The CLI correctly invokes `scanUserSources(..., "gate", ...)` before render, but every production adapter's default reader only `lstat`s a short list of dedicated plugin/skill/rule paths and returns them as `ambiguousPaths`. It never structurally reads the host's native user MCP/hook/plugin configuration, so fields such as `rawMcpPaths`, `manualHookPaths`, `manualRulePaths`, and `activePluginPaths` are populated only when a test injects `readUserSources`. For example, Codex never checks the raw MCP declarations in its user config; Claude, Cursor, and OpenCode have the same omission for their native config surfaces. The Plan 07 test at `tests/migration/manual-source-conflict.test.cts:28-53` uses a synthetic adapter that manufactures a conflict, so it proves orchestration ordering but not real discovery. A common manually registered KCodeRag source can therefore pass install/update/uninstall preflight and coexist with the managed source, violating the selected-host authority gate.

**Fix:** Implement bounded, secret-opaque structural readers for each supported host's actual user/native configuration surfaces. Inspect only registration keys, provider IDs, and source shapes; never retain or serialize URLs, headers, tokens, or bodies. Add filesystem-backed adapter tests (without injected metadata) for raw MCP, manual hook/rule, active plugin, ambiguous JSON/JSONC, and legacy Python registrations across all three mutation commands.

### CR-04: Capability-filtered update re-renders and updates all installed capabilities

**Classification:** BLOCKER  
**File:** `src/cli/commands.cts:529-550` (projection union: `src/hosts/claude.cts:184-191`)  
**Issue:** The CLI passes the requested update filter in `selectedCapabilities`, but each adapter's install selection helper unions that request with every capability already present in state. Claude's `selectedForInstall` returns `resolveCapabilitySelection([...existing, ...requested])`; Codex, Cursor, and OpenCode use the same pattern. The resulting contribution render reads current-package assets for the entire installed set, so `update --capability kcoderag-navigation` also replaces JX3 assets and advances their ownership/state bytes. This contradicts the documented independent lifecycle and the statement that repeated `--capability` flags filter update. The existing test at `tests/cli/commands.test.cts:876-913` checks default update and rejection of an absent capability, but never changes an unselected installed asset to prove it remains untouched.

**Fix:** Separate target membership (`installed` remains the complete composed state) from update scope (only requested contributors receive current-package bytes). Preserve validated bytes and ownership records for unselected contributors while composing the whole state, or introduce an explicit per-capability update projection contract. Add a two-capability test using a changed package asset and assert the unselected capability's bytes, digest, and mtime remain unchanged.
