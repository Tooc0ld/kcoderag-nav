# Phase 04.1: 多能力安装平台与 JX3 规范提示 - Context

**Gathered:** 2026-08-26
**Status:** Ready for research, then planning

<domain>
## Phase Boundary

将当前单一 KCodeRag 导航安装器重构为项目级、单宿主、可组合的内置 capability 平台，并交付两个可独立管理的能力：现有 KCodeRag QA navigation，以及无 Python、SVN 和网络依赖的 `jx3-style-nudge`。本阶段同时删除尚未公开使用的旧 CLI、旧状态 schema 和 QA/Dev 迁移兼容实现；对可能已经存在的手工 MCP、plugin 或 Python Hook 只做 secret-safe 识别并在写前硬停止，不迁移、接管或自动清理。

本阶段不实现远程 capability registry、第三方来源、传递依赖或确定性 JX3 扫描器。

</domain>

<decisions>
## Implementation Decisions

### 多能力平台与生命周期
- **D-01:** Phase 04.1 只管理随 `kcoderag-nav` npm 包发布的内置 capability。manifest、宿主投影和生命周期接口应可扩展，但不实现远程 registry、Git 下载、传递依赖、第三方信任或来源锁定。
- **D-02:** 未指定 capability 的交互式 `install` 先选择一个宿主，再多选 capability；自动化通过可重复的 `--capability` 显式选择。Navigation 与 `jx3-style-nudge` 可独立安装。
- **D-03:** `status`/`doctor` 默认展示所选宿主的全部 capability；`install` 添加所选能力；`update` 默认更新全部已安装能力并允许筛选；`uninstall` 必须交互选择或显式指定，绝不默认全删。
- **D-04:** 一次选择的 capability 集合先整体预检，再通过单宿主事务原子写入。任一能力冲突、不支持或漂移时整组不写；不做部分成功。
- **D-05:** 所有权、摘要、状态和配置 section 按 capability 记录。更新或卸载一个能力不得破坏另一个能力、其他宿主或用户配置。
- **D-06:** npm 包内保留一份 canonical Skill 模板；每个 host adapter 将确定性副本写入宿主原生项目目录，并分别记录所有权与摘要。跨宿主不共享受管文件，也不使用 symlink。
- **D-07:** 尚未发布使用的旧 CLI、旧状态 schema 与 QA/Dev 迁移兼容代码直接删除，不提供新旧状态迁移。可能存在的 pre-npm 手工 MCP、plugin、Python Hook 或多来源安装只读检测并硬停止，用户人工清理后重试；nav 不接管、不迁移、不自动删除。

### JX3 Skill 打包与规则内容
- **D-08:** Nav 安装纯 Markdown 的 `$jx3-code-style-correction` Skill 与独立的 CJS/JS nudge handler。安装后和运行时均不依赖 Python、SVN 或网络。
- **D-09:** Skill 以 `SKILL.md` 为紧凑入口，以自包含的 Markdown `references/` 承载详细规范；不依赖项目外部 Skill 或在线文档。
- **D-10:** Skill 是 nav 完整管理的受管资产，不允许直接编辑或建立 override 文件。项目特殊约定继续放在 `AGENTS.md` 等项目文档中。
- **D-11:** 指令优先级固定为：用户明确要求 > 项目文档 > JX3 Skill。发生冲突时说明冲突，不静默覆盖项目约定。
- **D-12:** R01–R19、S01–S08 从 scanner finding 条件改写为写前规范，并保留规则号以便未来审计能力追溯。不得把原扫描器使用说明原样当作新 Skill。
- **D-13:** 首次相关写入只注入短 nudge；Skill 默认加载 27 条规则的紧凑摘要，详细规则仅在当前改动风险相关时读取。不注册逐次写后 Hook。
- **D-14:** 任务结束前由模型对本任务实际修改区域做一次有界自查。明确的自引入问题做最小修正；需要业务判断或契约证据的问题只报告。不使用 SVN、scanner 或 PostToolUse 自查，也不声称“静态扫描通过”。
- **D-15:** Skill 缺失、损坏或摘要漂移时，nudge 静默 fail-open；`status`/`doctor` 报告 `capability_drift`，修复资产后才恢复提示。不使用 handler 内置的简版规则兜底。

### 写前触发与一次性语义
- **D-16:** 扩展名白名单大小写不敏感，固定为 `.c/.cc/.cpp/.cxx/.h/.hh/.hpp/.hxx/.inl/.ipp/.lua`；不按目录排除。
- **D-17:** 只处理能够可靠取得目标路径的结构化 Write/Edit/MultiEdit/apply_patch 类调用，不解析普通 shell。仅内容创建或修改触发；纯删除、纯重命名、未知路径跳过；单次多文件 patch 最多提示一次。
- **D-18:** 有稳定 `session_id`、`thread_id` 或 `conversation_id` 时，每个宿主会话/线程和项目边界只提示一次。没有稳定标识时完全静默，不用 TTL 猜测任务边界，也不逐次重复。
- **D-19:** 一次性 marker 存放在操作系统用户缓存的 `kcoderag-nav/nudges` 下，不污染项目。marker key 由 host、项目边界、capability 和稳定会话标识的哈希组成，不保存 prompt、tool input 或源文件路径；数量必须有界并可清理。
- **D-20:** 通过原子 exclusive create 竞争 marker，只有一个调用可以输出提示。权限、损坏、竞争、创建和清理异常全部静默 fail-open。

### 四宿主支持与版本证据
- **D-21:** 不允许将 instruction-only、toast、用户提示或可阻断事件伪装成 `native_pre_write`。每个 adapter 必须明确报告 delivery mode 与支持证据。
- **D-22:** Claude 使用经官方协议和 fixture 验证的 native pre-write。Codex、Cursor 与 OpenCode 只有在真实宿主 fixture 证明结构化目标路径、稳定会话标识和非阻断模型上下文注入后才允许安装 `jx3-style-nudge`。
- **D-23:** Codex 与 Cursor 设置经研究验证的最低宿主版本；更旧版本直接拒绝，不降级为 instruction-only。OpenCode 若无法证明非阻断模型上下文注入，也直接拒绝，不降级为 Skill-only 或 toast。
- **D-24:** Adapter 在安装预检中以固定宿主命令、短超时读取并严格解析版本。命令不存在、超时、无法解析或低于最低版本时，对 nudge 返回稳定的 `host_version_unsupported`；不得回显任意子进程输出，也不允许参数绕过。单独安装 navigation 不受 nudge 版本门禁影响。

### 提示正文
- **D-25:** 各宿主的协议包装可以不同，但注入给模型的正文语义固定：在本次 C/C++/Lua 修改前加载并遵循 `$jx3-code-style-correction` 的紧凑写前清单；用户和项目指令优先；结束前只自查实际修改区域。正文不包含文件内容、规则全文或“扫描通过”声明。

### Skill 内容研究门
- **D-26:** 在实现规划前必须先完成独立的 Skill 内容研究。首先取得并归档 2026-08-25 v5 的完整 `SKILL.md`、`references/` 和规则定义；当前 WPS 摘要不足以恢复 R01–R19/S01–S08。完整源不可得时研究阻塞，不得根据规则号或摘要编造内容。
- **D-27:** `04.1-RESEARCH.md` 必须包含：现有内容清单；27 条规则的原意、写前适用性、误报/上下文边界、摘要与详细引用归属、建议动作矩阵；新的 Skill 信息架构与 token 预算；代表性的 C/C++/Lua 正反例和行为验收提示。
- **D-28:** 研究应对照 Agent Skills 规范、OpenAI/Anthropic 官方 Skill 指南和成熟开源 Skill，逐条决定保留、改写、拆分、按需加载、删除或移交未来 `jx3-style-audit`。研究结论是 plan 的必需输入，不能把 Python scanner 或 SVN 工作流带回 nudge。

### the agent's Discretion
- Capability manifest 的具体字段名、内部 registry 代码结构和 adapter API 形状，由 researcher/planner 在保持上述产品契约的前提下确定。
- Codex、Cursor、Claude 与 OpenCode 的确切最低版本必须由 research fixture 得出，不在 CONTEXT 中猜测。
- 固定 nudge 的最终中英文措辞、references 的分类边界、marker 的容量/清理阈值和固定版本探测命令由 research/planning 确定，但不得改变已锁定语义与 fail-open 边界。

</decisions>

## Existing Code Insights

### Reusable Assets
- `HostAdapter`: 已把宿主检测/渲染与写入分离，可扩展为 capability-aware host projection，而不让 adapter 直接写文件。
- `applyTransaction`: 已提供 expected digest、state-last、完整回滚和安全路径检查，应继续作为一次所选 capability 集合的唯一提交边界。
- `update-check.cts`: 已实现稳定 session/thread/conversation ID 提取、SHA-256 marker key 和 `wx` 独占创建；应抽成共享 marker utility，避免 nudge 重复实现。
- `grep-nudge.cts`: 已展示 bounded input、协议专用 stdout 和全异常 fail-open 的 Hook 边界，可复用其测试与 launcher 模式。

### Established Patterns
- CLI 一次只管理一个宿主，跨宿主安装可以共存；capability 组合不能破坏这一边界。
- Canonical TypeScript `.cts` 编译成用户可运行 CJS；用户路径只能依赖 Node.js 22+ built-ins。
- Adapter 只读/渲染，CLI 编排，transaction 独占写入；状态与诊断必须 path-only、secret-safe、digest-backed。
- 受管文件漂移、symlink、特殊文件、模糊所有权和活动重复来源必须在写前硬停止。

### Integration Points
- `src/cli/commands.cts`：增加 capability selection、命令默认语义、版本预检与组合编排。
- `src/hosts/*.cts`：把 capability manifest 投影成各宿主原生 Skill、Hook/plugin/Rule 与配置 section。
- `src/core/state.cts` / `src/core/contracts.cts`：建立 capability-scoped ownership/status schema，删除未发布旧 schema 的迁移兼容路径。
- `src/core/transaction.cts`：接收完整的单宿主、多 capability desired state，保持一次原子提交。
- `src/hooks/`：共享 dispatcher、once marker utility 与 `jx3-style-nudge` handler；单能力异常不得污染其他能力或阻断宿主写入。
- `plugin-src/` 与 generator/pack gates：把两种内置 capability 的 canonical assets 确定性纳入 npm 包。

</code_context>

<specifics>
## Specific Ideas

- Nudge 正文保持约 1–3 行，只让模型加载 `$jx3-code-style-correction` 并在结束前做有界自查；规则正文留在 Skill 的渐进披露结构中。
- 未来 manifest 至少需要表达 capability identity、assets、host event/delivery mode、扩展名过滤和宿主支持证据；确切 schema 由 research/planning 决定。
- `status`/`doctor` 必须让用户看见 capability 粒度的 installed、drift、unsupported 和 delivery mode，而不显示配置正文或宿主命令原始输出。

</specifics>

- 远程 capability registry、Git 来源、第三方信任、传递依赖和来源 lockfile 留给未来独立阶段。
