## Critical Issues

### CR-01: Claude additive install treats any existing state as ownership of the project MCP entry

**Classification:** BLOCKER  
**File:** `D:/AIProgram/kcoderag-nav/src/hosts/claude.cts:377`  
**Issue:** `projectContributions()` passes `state !== undefined` to `mergeMcp()`. A valid Claude installation can contain only `code-style-nudge`, so the mere presence of state does not prove ownership of `.mcp.json` or its `kcoderag-qa` server entry. On a later additive install of `kcoderag-navigation`, an unmanaged same-name project entry bypasses the conflict at lines 309-315 and is overwritten. This violates the explicit ownership boundary and can replace manually managed connection settings instead of refusing before the transaction. A compiled-runtime reproduction confirmed that the style-only state is healthy, no ownership conflict is raised, and the unmanaged entry is projected for replacement. Existing smoke coverage exercises the happy style-to-navigation path but not this reverse-order conflict case.

**Fix:** Derive ownership from the previous file/section record, not from global state existence, and add a zero-write regression test:

```ts
const mcpCurrent = readRegular(target, MCP_PATH);
const mcpOwned = previousFile(state, MCP_PATH) !== undefined;
const mcp = mergeMcp(mcpCurrent, packageRoot, mcpOwned);
```

The regression should install only `code-style-nudge`, add an unmanaged same-name project MCP entry, then request `kcoderag-navigation` and assert `unmanaged_name_conflict` plus a byte-for-byte unchanged project tree.

## Warnings

### WR-01: Contradictory MCP header aliases pass generation and can split host credentials

**Classification:** WARNING  
**File:** `D:/AIProgram/kcoderag-nav/src/generator/index.cts:521`  
**Issue:** The canonical environment source contains both `headers` and `http_headers`, but `connectionDetails()` silently selects `http_headers` whenever both are objects and never checks that their contents agree. The QA `.mcp.json` product is copied from the source as-is, while the Codex projection is rendered from the selected alias. OpenCode and ZCode prefer `headers`; Codex prefers `http_headers`. The current two maps are equal, but a one-sided maintenance edit is accepted by generation and can silently ship different connection authorization to different hosts. This is an avoidable secret-configuration ambiguity and a cross-host regression risk.

**Fix:** Either keep one canonical internal header map and render each host's required field name from it, or reject sources where both aliases exist but are not deeply equal. Add a generation test that supplies unequal aliases and expects a stable `environment_mismatch` failure without including either value in diagnostics.
