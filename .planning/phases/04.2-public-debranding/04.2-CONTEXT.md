# Phase 04.2: 公开版本去品牌化 - Context

**Gathered:** 2026-08-27
**Status:** Research complete; ready for planning

<domain>
## Phase Boundary

将当前 `kcoderag-nav` HEAD 和下一个公共 npm 版本中的代码规范能力改为完全中性的
`code-style-nudge` / `$code-style-correction`，并从本仓库全部 Git 跟踪路径和内容以及实际 npm
tarball 中移除游戏、产品和公司品牌语义族。改名必须保留能力平台、首次相关写入提示、fail-open、
事务、五宿主支持证据以及 `R01–R19`、`S01–S08`、`E01–E15` 的既有行为。

本阶段在规划前独立研究当前 Agent Skills 官方规范和成熟开源 Skill，允许在不改变规则语义的
前提下优化 Skill 的结构与措辞。阶段终点是让版本已固定为 `0.3.0` 的干净候选 HEAD 和同一实际
npm tgz 通过五宿主 readiness 门禁并生成 metadata-only 证据；本阶段不创建 tag、不 publish、
不从 registry 重新获取。旧 Git 历史、tag、release 和 npm 版本不重写、不撤回、不 unpublish。
本阶段从兄弟 KCodeRag 仓库中的旧体验指南一次性只读迁入仍有效内容，在本仓库建立并独占维护
`docs/MCP_QA_EXPERIENCE_GUIDE.md`；兄弟文件不再修改、同步或绑定，其本地副本纳入 Git/tgz 零命中扫描。

</domain>

<decisions>
## Implementation Decisions

### 屏蔽词范围

- **D-01:** 使用封闭的品牌语义词族，覆盖游戏/产品名称、公司名称及明显别名、英文译名、拼音、大小写、Unicode、全半角和空格/连字符/下划线变体；不使用模糊相似度。
- **D-02:** 当前 HEAD 的 Git 跟踪路径和内容不允许历史文档、旧证据、测试 fixture、用户名路径或引用场景例外。原始名称只保留在旧 Git 提交中。— **Reversibility:** costly — 放宽例外会使公开 HEAD 重新暴露已经清理的名称，并要求重新设计发布审计和证明边界。
- **D-03:** `KCodeRag`、`kcoderag-nav`、通用技术词、宿主名称、不直接拼出禁用品牌词的普通 URL，以及非品牌内部技术标识不属于屏蔽对象。
- **D-04:** 本仓库全部 Git 跟踪路径和内容进入零命中范围，包括新建的 `docs/MCP_QA_EXPERIENCE_GUIDE.md`。兄弟仓库旧指南仅作为一次性只读内容来源，不扫描兄弟仓库，也不修改或同步其文件。

### 中性命名体系

- **D-05:** capability ID 固定为 `code-style-nudge`，Skill 名固定为 `code-style-correction`。provider、hook、测试、资产目录、生成路径、receipt schema、状态 contributor ID 和用户提示全链路使用对应中性名称，不保留第二套内部别名。— **Reversibility:** one-way — `0.3.0` 发布后这些 ID 会成为 CLI、安装状态、文件路径和 npm 制品的公共契约，再改名需要新的破坏性版本。
- **D-06:** 规则 ID 改为 `R01–R19` 和 `S01–S08`，行为验收 ID 继续使用 `E01–E15`；不引入 `STYLE-` 前缀，也不重新设计语义化编号。
- **D-07:** 已经存在旧 capability 的本地测试状态对 `0.3.0` 是无效状态。`status/doctor` 只报告通用稳定码，install/update/uninstall 全部零写；不解析旧别名、不迁移、不自动清理。
- **D-08:** npm 包名 `kcoderag-nav` 和 navigation capability `kcoderag-navigation` 保持不变。代码规范能力只描述为通用 C/C++/Lua 写前指导，不出现游戏、行业或公司背景。

### Skill 研究与改动边界

- **D-09:** 规划前必须完成独立网络研究并生成 `04.2-RESEARCH.md`。研究对照当前 Agent Skills 官方规范、OpenAI/Anthropic Skill 指南和成熟开源 Skill，再由 planner 使用结论拆分实施计划。
- **D-10:** 允许优化 frontmatter、触发描述、紧凑索引、references 路由、重复内容、示例和 token 使用；不得改变 27 条 `R/S` 规则的约束含义或 `E01–E15` 的行为结论。
- **D-11:** 不含品牌词的宏、类型、协议常量、文件 API 和其他项目型技术术语继续保留。去品牌化不把具体规则泛化成失去操作价值的占位原则。
- **D-12:** 规则语义等价由维护者人工审阅 Skill diff 确认。既有 `E01–E15` 自动化回归继续保留并必须通过，但本阶段不新增改名前后规则映射矩阵。

### 零命中与发布门禁

- **D-13:** 发布审计采用分层候选：扫描干净 checkout 的 Git 跟踪路径和内容，并在构建后扫描实际 npm tarball 的成员名和可检查内容；不扫描 `.git` 历史、`node_modules` 或未提交草稿。
- **D-14:** 审计失败只输出稳定错误码、相对路径、路径/内容类别、位置和中性词族编号，不打印命中的品牌原文或周边内容。禁用词表自身不得以原始连续文本在源码或制品中产生自命中。
- **D-15:** 品牌词审计只在正式发布路径中硬阻断；普通本地提交和普通 CI 不接入该硬门禁。Phase 04.2 完成验证和每次 npm 发布仍必须先通过源码与 tarball 零命中审计。
- **D-16:** Phase 04.2 只验证 exact `0.3.0` 候选的 readiness：以冻结 commit/tree、同一个实际 npm tgz 及其 SHA-256 绑定源码零命中、制品身份、五宿主安装生命周期和既有完整门禁；`tag`、`publish` 与 `registry_refetch` 必须记为 `NOT_RUN_BY_SCOPE` 或不进入必需检查，不得伪记为 PASS。后续发布需要独立授权，已发布不可变版本发现问题只以前进版本修复，不回退 tag/latest、不 unpublish。— **Reversibility:** reversible — 后续可在独立发布阶段消费已绑定的 readiness 证据，但不能追认本阶段未执行的外部动作。
- **D-17:** Phase 04.2 将 Codex、Claude Code、Cursor、OpenCode 与 ZCode 全部纳入 capability 改名后的 required packaged lifecycle/smoke 验收。navigation 在五宿主保持可用；代码规范能力仍只允许冻结 PASS receipt 对应的 Claude Code `2.1.241`，Codex、Cursor、OpenCode 与 ZCode 必须保持 `host_version_unsupported` 零写。ZCode 真机 workspace trust/admission 与版本冻结仍由 Phase 06 负责，本阶段不得提前宣称。— **Reversibility:** costly — 再次移除第五宿主会使公共 host union、package inventory 和验收矩阵不一致。
- **D-18:** Phase 04.2 在 `docs/MCP_QA_EXPERIENCE_GUIDE.md` 建立仓库内唯一维护副本，只迁入当前仍有效且完成中性化的内容；后续安装、卸载、更新、宿主兼容、路由、hook 和发布说明只更新该本地文件。`../KCodeRag/MCP_QA_EXPERIENCE_GUIDE.md` 只读且不得被 CLI、维护脚本或 readiness 修改、同步、摘要绑定。— **Reversibility:** costly — 双向同步会重新引入跨仓库写权限和证据耦合。

### the agent's Discretion

- 封闭词族在源码中的非自匹配编码、Unicode/分隔归一化实现、文本/二进制判定、大小上限和中性词族编号由 researcher/planner 决定，但不得削弱 D-01、D-02、D-13 和 D-14。
- 独立研究可选择额外成熟开源 Skill 作为对照；必须优先使用当前官方规范和上游仓库，不以二手博客替代权威来源。
- Skill 的具体段落拆分、references 文件边界和中英文措辞可根据研究优化，只要满足 D-10 至 D-12。
- `0.3.0` readiness receipt 形状、单一实际 tgz 的临时目录和五宿主 smoke 编排由 planner 确定；不得设计 tag/publish 分支，敏感配置继续保持 opaque、secret-safe。

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `CapabilityProvider`、registry 和 compose 层已经把 capability 身份、宿主支持和文件/section 贡献集中起来；中性改名应沿闭集传播，而不是新增并存别名。
- Generator、pack audit 和 package `files` allow-list 已有 exact inventory 模式，可扩展为源码/tarball 的路径与内容零命中检查。
- Retirement audit、pre-release evidence 和 release helper 已有确定性排序、stable code、receipt 绑定和不可变 fix-forward 模式。
- 当前 Skill 完整性测试和 `E01–E15` 行为测试可作为改名及低风险措辞优化的回归基线。

### Established Patterns

- TypeScript `.cts` 是唯一维护源码，发布 CJS 仅依赖 Node.js 22+ built-ins；品牌审计不得增加生产依赖或运行时编译器。
- Canonical templates 生成 QA/Cursor/宿主资产，生成产物不能手工维护；名称变更必须从规范源确定性传播。
- Adapter 只 read/render，transaction 独占项目写入；capability 改名不能绕过 current-state、摘要、漂移和回滚边界。
- CLI、hook、receipt 和诊断只输出稳定安全字段，不泄露配置正文、网络地址、凭据或任意子进程输出。

### Integration Points

- capability 类型、registry、provider、state parser、CLI flag/help、adapter target paths 和 hook dispatcher 共同形成旧 ID 的完整调用面。
- `plugin-src/`、generator inventory、generated QA/Cursor trees、package allow-list、smoke fixture 和 tests 共同形成路径与内容改名面。
- planning、README、AGENTS、receipt、CI/release workflow 和仓库内体验指南形成公开文档与证据改名面；兄弟指南不再是写入或证据目标。
- release-readiness path 需要对冻结 Git subject 与同一个实际 `0.3.0` tgz 运行零命中、pack 和五宿主 smoke，并证明命令没有修改 HEAD、index、refs、tag 或 registry。

</code_context>

## Specific Ideas

- 最终用户看到的能力组合是 `kcoderag-navigation` 与 `code-style-nudge`；Skill 调用名是 `$code-style-correction`。
