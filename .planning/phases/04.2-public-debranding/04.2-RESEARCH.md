## Implementation Decisions

### 屏蔽词范围

- **D-01:** 使用封闭的品牌语义词族，覆盖游戏/产品名称、公司名称及明显别名、英文译名、拼音、大小写、Unicode、全半角和空格/连字符/下划线变体；不使用模糊相似度。
- **D-02:** 当前 HEAD 的 Git 跟踪路径和内容不允许历史文档、旧证据、测试 fixture、用户名路径或引用场景例外。原始名称只保留在旧 Git 提交中。— **Reversibility:** costly — 放宽例外会使公开 HEAD 重新暴露已经清理的名称，并要求重新设计发布审计和证明边界。
- **D-03:** `KCodeRag`、`kcoderag-nav`、通用技术词、宿主名称、不直接拼出禁用品牌词的普通 URL，以及非品牌内部技术标识不属于屏蔽对象。
- **D-04:** 本仓库全部 Git 跟踪路径和内容进入零命中范围，包括仓库内 `docs/MCP_QA_EXPERIENCE_GUIDE.md`；兄弟仓库旧指南仅作为一次性只读迁入来源，不修改、不同步、不绑定其摘要。

### 中性命名体系

- **D-05:** capability ID 固定为 `code-style-nudge`，Skill 名固定为 `code-style-correction`。provider、hook、测试、资产目录、生成路径、receipt schema、状态 contributor ID 和用户提示全链路使用对应中性名称，不保留第二套内部别名。— **Reversibility:** one-way — `0.3.0` 发布后这些 ID 会成为 CLI、安装状态、文件路径和 npm 制品的公共契约，再改名需要新的破坏性版本。
- **D-06:** 规则 ID 改为 `R01–R19` 和 `S01–S08`，行为验收 ID 继续使用 `E01–E15`；不引入 `STYLE-` 前缀，也不重新设计语义化编号。
- **D-07:** 已经存在旧 capability 的本地测试状态对 `0.3.0` 是无效状态。`status/doctor` 只报告通用稳定码，install/update/uninstall 全部零写；不解析旧别名、不迁移、不自动清理。
- **D-08:** npm 包名 `kcoderag-nav` 和 navigation capability `kcoderag-navigation` 保持不变。代码规范能力只描述为通用 C/C++/Lua 写前指导，不出现游戏、行业或公司背景。

### Skill 研究与改动边界

- **D-09:** 规划前必须完成独立网络研究并生成 `04.2-RESEARCH.md`。研究对照当前 Agent Skills 官方规范、OpenAI/Anthropic Skill 指南和成熟开源 Skill，再由 planner 使用结论拆分实施计划。

### 零命中与发布门禁

- **D-13:** 发布审计采用分层候选：扫描干净 checkout 的 Git 跟踪路径和内容，并在构建后扫描实际 npm tarball 的成员名和可检查内容；不扫描 `.git` 历史、`node_modules` 或未提交草稿。

- **D-15:** 品牌词审计只在正式发布路径中硬阻断；普通本地提交和普通 CI 不接入该硬门禁。Phase 04.2 完成验证和每次 npm 发布仍必须先通过源码与 tarball 零命中审计。
- **D-16:** Phase 04.2 只验证 exact `0.3.0` 候选 readiness：冻结 Git subject 与同一个实际 npm tgz 必须绑定零命中、制品身份、五宿主 lifecycle/smoke 和既有门禁；本阶段不创建 tag、不 publish、不 registry refetch，外部动作必须保持 `NOT_RUN_BY_SCOPE`。后续发布需独立授权，已发布不可变版本只允许 fix-forward。

## Official/Open-Source Skill Findings and Current Skill Audit Matrix

### Source-backed design findings

- Agent Skills requires a directory whose name matches frontmatter ``name``; names are lowercase/hyphenated, descriptions state what the Skill does and when it applies, and the full body is loaded only after activation. It recommends a compact ``SKILL.md`` and shallow relative references for progressive disclosure.[CITED: https://agentskills.io/specification]
- OpenAI documents three disclosure levels—metadata, full instructions, then referenced resources—and emphasizes a concise, front-loaded description for reliable implicit activation. It treats an instruction-only Skill as the default and recommends scripts only when deterministic execution or an external tool is actually needed.[CITED: https://developers.openai.com/codex/skills]
- Anthropic's upstream skill-creator likewise treats ``description`` as the primary trigger, recommends realistic should-trigger and should-not-trigger evaluations including near misses, and keeps details in one-level references rather than nesting reference chains.[CITED: https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md]
- Two mature upstream patterns are useful but should be adopted selectively: Vercel's guideline Skill is a very small router to one authoritative rules source, while Superpowers' writing-skills material provides strong trigger/evaluation discipline but is much larger and more prescriptive than this repository needs.[CITED: https://github.com/vercel-labs/agent-skills/blob/main/skills/web-design-guidelines/SKILL.md][CITED: https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md]

## Deterministic Zero-Hit Audit Design Options and Recommendation

### Options

| Option | Determinism | Coverage | Self-match risk | Decision |
|---|---|---|---|---|
| Recursive filesystem walk + regex | Low: includes untracked drafts, ignored build output and platform artifacts | Does not prove a specific commit or package | High if raw terms live in scanner/tests | Reject. |
| ``git grep`` plus ``npm pack --dry-run`` manifest | Medium | Grep/path variant handling is incomplete; dry-run inventory does not prove inspected tgz bytes | Medium | Reject as release evidence. |
| **One encoded closed matcher over exact Git objects and one actual tgz** | High | Proves tracked paths/blobs and package members/bodies using identical semantics | Low by construction | **Use.** |

Git documents ``ls-tree`` as listing a tree object's contents and provides recursive, full-tree and NUL-terminated output; ``cat-file --batch`` reads objects without checking out or printing them through a shell pipeline.[CITED: https://git-scm.com/docs/git-ls-tree][CITED: https://git-scm.com/docs/git-cat-file] npm documents that ``npm pack`` creates the tarball, that ``--json`` emits machine-readable data, and that ``--pack-destination`` selects its output directory.[CITED: https://docs.npmjs.com/cli/v11/commands/npm-pack/] npm's package ``files`` rules determine the allow-list and always exclude ``.git``, ``.npmrc`` and ``node_modules`` from packages.[CITED: https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#files]

### Recommended architecture

```text
family definitions (encoded code points/fragments; IDs F001...)
                         |
                         v
                 pure normalize + match
                  /                   \
Git adapter                               npm-tar adapter
ls-tree -r -z <subject>                   one real .tgz
cat-file --batch <oids>                   validated tar parser
paths + blob bytes                        member names + bodies
                  \                   /
                   safe metadata finding
       { code, scope, familyId, relativePath, line/offset }
```

#### 1. One pure closed-family matcher

ECMAScript ``String.prototype.normalize("NFKC")`` applies Unicode compatibility decomposition followed by canonical composition; UAX #15 explains that compatibility normalization folds width and other compatibility distinctions and guarantees normalization-form stability across Unicode versions.[CITED: https://tc39.es/ecma262/multipage/text-processing.html#sec-string.prototype.normalize][CITED: https://www.unicode.org/reports/tr15/]

**Recommendation:** define a closed list of semantic families from D-02, each with a neutral opaque ID such as ``F001`` and one or more aliases encoded as code-point arrays or non-contiguous fragments. Never place a prohibited raw term in scanner source, emitted CJS, test names, fixtures, snapshots or messages. At runtime:

1. Strictly decode known text encodings (UTF-8, UTF-8 BOM, UTF-16LE BOM, UTF-16BE BOM).
2. Apply ``normalize("NFKC")``.
3. Apply locale-independent ``toLowerCase()``.
4. Remove only Unicode whitespace, Unicode dash punctuation ``\p{Pd}``, ASCII/full-width forms already folded by NFKC, and underscore.
5. Match only the closed aliases; do not use fuzzy distance, transliteration or arbitrary semantic expansion.

For paths, first validate and normalize separators to ``/``, retain ``/`` as a hard boundary, and normalize/match each path component. This catches case, Unicode/full-width, space/hyphen/underscore variations without falsely joining unrelated adjacent directories. The same function must be called for Git paths, Git bodies, tar member paths and tar bodies.

#### 2. Commit-exact tracked source inventory

Run Git with an argument array and ``shell: false``: ``git ls-tree -r -z --full-tree <candidate-subject>``. Parse every NUL-delimited record into mode/type/OID/path, reject malformed records and unsupported tracked object types, and request every blob by OID via one bounded ``git cat-file --batch`` session. This proves the chosen subject even when the worktree contains unrelated drafts. It inherently does not traverse ``.git`` internals; explicitly reject/skip any tracked ``node_modules/`` path according to D-13 rather than treating it as ordinary content.

The scanner must not use ``git ls-files`` as release evidence: that describes the index/working context, not necessarily the immutable subject being attested. It also must not read worktree file contents after enumerating the tree, because a concurrent edit could change the bytes between inventory and scan.

#### 3. Actual npm tar inventory

Create exactly one candidate tarball in a newly created private temporary directory using ``npm pack <clean-candidate-root> --ignore-scripts --json --pack-destination <dir>``. Parse only bounded JSON stdout, validate the returned filename stays inside that directory, and calculate SHA-256 on the resulting bytes with ``node:crypto``; Node 22 documents ``createHash`` for incremental hashing.[CITED: https://nodejs.org/docs/latest-v22.x/api/crypto.html#cryptocreatehashalgorithm-options]

Reuse or extract the existing bounded gzip/tar reader from ``pack-audit`` instead of spawning a platform ``tar`` executable. Inspect **every** validated tar member name and every inspectable member body. Reject absolute/traversal names, duplicate normalized names, links/devices/special entries, truncated records, unsupported encodings and resource-limit overflow. Assert that prohibited infrastructure members such as ``node_modules/`` are absent rather than silently accepting them. The pack member allow-list audit, scanner and smoke harness must all receive this same tgz pathname/SHA, not independently repack the directory.

**Recommended fail-closed resource limits:** 64 MiB archive, 8 MiB per member/blob, 4,096 members and 4,096 bytes per path. These values are design recommendations within the agent's discretion, not external standards; tests should prove the boundary behavior. If a future allowed binary member cannot be decoded sufficiently to prove all closed Unicode variants absent, readiness fails with a neutral ``unsupported_content``-style code rather than skipping it.

#### 4. Self-match prevention and safe diagnostics

Use encoded family construction plus tests that synthesize positive variants from numeric code points. The source scanner must scan its own tracked source and compiled product normally; no scanner-file exclusion is allowed. A family definition that accidentally materializes a prohibited spelling therefore fails the same gate it implements.

Return findings only as metadata:

| Field | Allowed values |
|---|---|
| ``code`` | Stable neutral finding/failure code. |
| ``scope`` | ``git_path``, ``git_content``, ``tar_path`` or ``tar_content``. |
| ``familyId`` | Opaque ``F###``; never the matching alias. |
| ``relativePath`` | Normalized safe path relative to repository or package root. |
| location | Line/column for decoded text or bounded byte offset; no excerpt. |

Never emit the match, surrounding content, Git/npm stdout or stderr, config bodies, URLs, headers or credential values. MCP/host configuration is scanned **lexically as opaque bytes/text only**: do not JSON/TOML-parse fields, interpret endpoints, recognize bearer formats or inventory key/value pairs. A finding says only that a family occurred at a safe path/location.

### Don't Hand-Roll

| Problem | Do not build | Use instead | Reason |
|---|---|---|---|
| Unicode normalization | Home-grown width/case tables | ECMAScript ``normalize("NFKC")`` plus a closed separator fold | Standards-defined normalization and stable runtime behavior.[CITED: https://tc39.es/ecma262/multipage/text-processing.html#sec-string.prototype.normalize] |

## Pitfalls, Security/Privacy Boundaries, and Windows/Linux Concerns

### Common pitfalls

| Pitfall | What goes wrong | Prevention / warning sign |
|---|---|---|
| Global string replacement | Non-brand technical identifiers, frozen receipt bytes or behavioral prose change. | Closed family scope; canonical-first edits; manual semantic diff; exact receipt digest remains unchanged. |
| Alias “for safety” | Old state continues parsing, scanner cannot reach zero, and migration behavior reappears. | New-only unions/parser/registry; explicit old-state zero-write tests. |
| Scanning the worktree | Untracked drafts cause false failures or concurrent edits evade proof. | Scan Git OIDs at one frozen subject. |
| Scanner excludes itself | Raw prohibited terms hide in encoded rules/tests/generated CJS. | Numeric/fragments only; scan every tracked scanner artifact normally. |
| Repacking per gate | Pack audit, scanner and smoke attest different tgz bytes. | One orchestrator-owned tgz/hash, shared by all consumers. |
| Treating ``npm pack --dry-run`` as the artifact | Only a manifest prediction is inspected. | Open and inspect the actual tgz produced by ``npm pack``. |
| Printing a match for debugging | Credential/config text leaks into CI or receipts. | Metadata-only finding shape; no excerpts/stdout/stderr. |
| Claiming Cursor hook equivalence | Public docs overstate runtime behavior. | Preserve Rule + Skill semantics and name the native success event only. |
| Treating orphan markers as migration targets | Rename gains unintended OS-cache deletion authority. | Leave old markers untouched; D-19 manual reset only. |
| Running zero-hit in normal CI | Contradicts locked D-15 and changes developer workflow. | Invoke only formal readiness command; unit-test scanner everywhere. |

### Security domain

[VERIFIED: `.planning/config.json:46-49`] ``"security_enforcement": true`` and ``"security_asvs_level": 1``. This is a local file/package assurance phase, so authentication, session management, browser access control and cryptographic protocol design are not introduced. Applicable controls are input/path validation, safe file handling, bounded resource use, integrity hashing and secret-safe output.

OWASP ASVS identifies file handling and untrusted data validation as security verification areas; its current official project page publishes ASVS 5.0.0, and the official V5 material covers validation boundaries and file/path risks.[CITED: https://owasp.org/www-project-application-security-verification-standard/][CITED: https://github.com/OWASP/ASVS/tree/master/5.0/en/0x15-V5-Validation-Sanitization-Encoding]

| ASVS category | Applies | Control in this phase |
|---|---|---|
| V2 Authentication | No | No authentication behavior changes; credential inputs remain opaque. |
| V3 Session Management | No | No web/user session is introduced; once-marker is a local bounded hint, not authorization. |
| V4 Access Control | Limited | Candidate subject and declared package/host roots are the only readable/mutable scopes. |
| V5 Validation/Sanitization/Encoding | Yes | Strict Git/tar record parsing, path containment, Unicode decoding/normalization, size/count bounds, reject ambiguity. |
| V6 Cryptography | Yes, integrity only | Use Node ``createHash("sha256")``; do not hand-roll hashing or treat a digest as authentication.[CITED: https://nodejs.org/docs/latest-v22.x/api/crypto.html#cryptocreatehashalgorithm-options] |

| Threat | STRIDE | Mitigation |
|---|---|---|
| Tar path traversal/link member | Tampering/Elevation | Normalize and reject absolute, ``..``, link/device/special entries before reading/extracting; scanner need not extract at all. |
| Decompression bomb/oversized object | Denial of service | Archive/member/path/count bounds and bounded subprocess output; fail closed. |
| Git/npm output injection | Spoofing/Information disclosure | ``shell:false`` argument arrays, NUL/binary protocols, parse bounded machine format, never echo raw output. |
| TOCTOU between scan/pack/smoke | Tampering | Immutable subject + clean isolation + one hash-bound tgz. |
| Config/credential disclosure | Information disclosure | Opaque lexical inspection, metadata-only diagnostics/receipts, safe relative paths. |
| Unicode bypass | Tampering | NFKC + deterministic case/separator fold + closed alias tests, same core in both inventories. |

### Windows/Linux implementation concerns

- Invoke Node subprocesses with ``shell: false`` and explicit argument arrays. On Windows, resolve the npm executable using the repository's established ``npm.cmd`` handling; do not assemble ``cmd /c`` strings from paths or user input.
- Parse Git ``-z`` output as bytes/NUL records so spaces, tabs, quotes and non-ASCII paths survive. Convert diagnostics to validated POSIX-style relative paths, but use ``path.resolve``/``path.relative`` for containment on the active OS.
- Never compare raw platform separators in package manifests: tar paths are ``/``-separated; repository paths require a single normalization boundary.
- Use private ``mkdtemp`` directories, close file handles before cleanup, and test Windows antivirus/file-lock cleanup failures. Cleanup failure may report a safe temp-relative code but must not mutate the repository or publish.
- Set deterministic child environment deliberately and do not inherit/read credential values for diagnostics. Preserve required npm/Git runtime environment without serializing it.

## Concrete Planning Implications / Suggested Plan Boundaries

### Required architecture patterns

1. **Closed identity, no migration:** compile-time capability union, runtime parser, registry and generated inventories all accept only ``code-style-nudge``. Unsupported/old state stops before desired-state creation and before the shared transaction.
2. **Canonical-first generation:** edit/rename ``plugin-src`` and TypeScript sources, then regenerate deterministic products. Generated QA/Cursor/CJS trees are outputs, not independent editing surfaces.

5. **Evidence as metadata:** aggregate stable check IDs/digests/counts only. Human semantic review is a signed/verdict checkpoint, not a copied rule matrix.
